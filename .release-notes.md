## MWORKS AI for DeepSeek Harness — v1.0.0

First public release. `dsh-mworks-ai` plugs the official MWORKS tooling into DeepSeek Harness so the agent can drive Syslab (Julia) and Sysplorer (Modelica) the same way the official Syslab AI and Sysplorer AI assistants do.

### What's inside

- **MCP servers** — `mcp__mworks_syslab__*` (8 tools: Julia execution, environment detection, help search, MATLAB→Julia mapping) and `mcp__mworks_sysplorer__*` (15 tools: session, library, model, check, translate, simulate, layout, results, plotting, API/model docs, resources).
- **`mworks_environment` tool** — reports the MWORKS installation it found: Syslab and Sysplorer roots, versions, the Julia runtime and the MCP entry points.
- **Official working rules** — Syslab requires `read_syslab_skill` → `detect_syslab_toolboxes` before any code execution; prefer `Ty*` packages; confirm APIs from local help; call `session_manager` before other Sysplorer tools; never write modeling outputs into the installation directories.
- **UI** — a *Runtime environment* section on this bundle's own page under **Plugins**: detected installations and versions, the Julia runtime, both MCP servers with path status, and the MWORKS skills the session can call, plus a **Re-detect** button. Nothing is added to the conversation.

### Install

```bash
npm install --save-dev dsh-mworks-ai
```

### Requirements

- A local MWORKS installation. `cordis.patch.yml` is written for Syslab `E:\MWORKS\Syslab 2026b`, Sysplorer `E:\MWORKS\Sysplorer 2026b` and Julia `C:\Users\Public\TongYuan\julia-1.10.10`; edit it if MWORKS lives elsewhere. The Runtime environment section and `mworks_environment` report what is actually found.
- The MWORKS skills you want the agent to follow, installed into a skill root the harness scans.

### Checks

`npm test` runs the three dependency-free checks in `test/` (render contract, CSS class coverage, display metadata).

## MWORKS AI for DeepSeek Harness — v1.1.0

Fixes the failure mode where a MWORKS MCP server went silent and every call blocked until its timeout.

### What changed

- **The two MCP servers are contributed through the Host MCP manager** (`ctx.mcpManager.register`) instead of bare `@deepseek-ai/dsh-mcp-client` rows. Their connection state is now readable, and either one can be rebuilt in place.
- **`mworks_mcp_status`** — reports each server's live state (connecting / connected / reconnecting / failed), registered tool count and last error.
- **`mworks_mcp_restart`** — remounts one MCP child, which re-runs engine discovery and re-attaches it to the running Sysplorer. This does not restart Sysplorer or DeepSeek Harness.
- **The Runtime environment section shows live state** with a **Reconnect** control for a server that is not connected, plus a `POST /api/dsh-mworks-ai/restart` route behind a same-origin check and a server allowlist.
- **The agent instructions gained the recovery rule**: a MWORKS call that stopped answering is not fixed by retrying; read `mworks_mcp_status`, rebuild the server, then re-verify. The section also warns that `session_manager(restart|full_reset)` drives the Sysplorer engine that every other MWORKS window shares, so it must not be used to recover the bridge.

### Why retrying could not work

When Sysplorer restarts underneath a running session, the MCP child stays alive but remains attached to the old engine port. It emits no close and no error, so the client bridge has nothing to reconnect on — the automatic reconnect only fires when the child actually exits. Every later call then blocks until `toolCallTimeoutMs`. Remounting the child is the fix; verified by killing a wedged child and by `mworks_mcp_restart`, both of which produced a fresh child attached to the live port.

### Requirement

The profile must mount `@deepseek-ai/dsh-mcp-manager` (the Web and Desktop profiles do). Without it the plugin loads but contributes no MCP servers, and the report says so.

## MWORKS AI for DeepSeek Harness — v1.1.1

The MWORKS skills no longer depend on another AI client being installed, and the plugin no longer carries any machine path.

### What changed

- **No hardcoded paths.** The plugin used to name one machine's installation directories and the MCP executable under them. It now resolves each installation at load time — this row's config, then the environment, then a directory scan — and derives the command, args and working directory from what it found. A product that is not installed contributes no server at all. The modeling workspace defaults to `~/.dsh-mworks-ai/workspace`.
- **Skills are registered from the MWORKS installation.** The plugin reads the bundles under `<Sysplorer>/Tools/sysplorer_mcp/resources/modeling_skills` and `<Syslab>/Tools/syslab-skills` and registers them into the session, like a skill bundle registers its own `skills/` directory. Before, they reached the catalog only because the MWORKS installers copy them into `%USERPROFILE%\.config\opencode\skills` and another plugin happened to scan that folder — so the skills disappeared whenever that plugin was absent.
- **Gap fill by name.** A skill the registry already resolves is left to its provider; only missing names are registered. `registerSkills: false` on the row opts out entirely.
- **Frontmatter is parsed properly.** Folded (`>-`) and literal (`|`) descriptions are unfolded; previously a naive reader would have taken `>-` as the description. Each registration carries a directory `resourceBase`, so `references/` resolves against the installed bundle.
- **The report tells the truth.** It asks the skill registry instead of guessing from disk, so it also counts the skills whose names did not match the old prefix filter (`ta-vehicle-modeling`, `sysplorer-mds-docs`), and it says whether the answer came from the registry or from disk.

### Verified by

Disabling the external skill provider dropped all 36 MWORKS skills from the catalog; reloading this plugin restored all 36, and loading one reported its base directory as the MWORKS installation path rather than the OpenCode copy. On this machine the resolved entries still started both servers and reported 8 and 15 registered tools.

The host check no longer needs MWORKS installed: it builds a throwaway fixture installation, points the plugin at it, and asserts the resolved command lines, the skill registration, the folded frontmatter and the shared-folder name filter. It also reads `lib/index.js` and fails if a drive path literal is reintroduced.
